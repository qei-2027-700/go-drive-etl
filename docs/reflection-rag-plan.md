# 振り返り回答機能の検討メモ

検討日: 2026-10-11（日本時間）。会話で整理した方向性を保存したもの。以下の追加機能は未実装であり、既存 Issue の完了条件を変更したものではない。

## 目的とデータの役割

「先月の振り返りで、何を課題にしていた？」に、文書を根拠として出典付きで回答する。

- Drive: 元の Markdown 文書を置く。
- Go ETL: 文書を取得し、本文をチャンクに分割して BigQuery へ保存する。
- Bronze (`chunks`): 本文チャンクと内容のバージョンを保存する。
- `chunks_current`: 最新の本文を重複なく公開する View。
- Silver (`silver_chunks`): 最新本文を検索・集計に利用しやすい形で公開する。
- Gold: 日別・ファイル別の取り込み状況を集計し、データポータルで表示する。本文の代わりにはならず、振り返り回答では参照不要。

Gold の結果は BigQuery に残り、Drive の CSV はそのコピーである。CSV 再配信は RAG に必要なく、利用者にレポートを届ける用途がなければ削除候補とする。実際の削除と Issue #115 の条件変更は別途行う。

## 現在の日付と必要な追加情報

現状の `ingested_at` は取り込み日時。Silver の `ingested_date` は `DATE(ingested_at, "Asia/Tokyo")` であり、振り返りの対象日付ではない。Silver → Gold でも振り返り日付を抽出していない。意図的に除外した理由は確認できず、振り返り固有の情報抽出は未実装。

文書名や本文に日付が含まれていても、SQL で絞り込める日付列にする処理が必要。Drive の作成・更新日時は振り返り対象日と一致するとは限らない。

実際の文書形式を確認してから、以下の仕様を決める。

- 日次は `reflection_date`、週次など期間を持つ文書は対象期間の開始日・終了日を候補とする。
- ファイル名・本文の見出し・メタデータのどこを日付の取得元とするか、競合時の優先順位を定義する。
- 抽出できない日付を取り込み日で代用しない。欠損を明示し、必要に応じて対象外・要確認として表示する。
- 文書名と Drive URL を出典用に保持する。
- Go でチャンク分割前に文書全体から日付を抽出し、各チャンクに付ける。Silver で公開する。
- 保存型・Protobuf・BigQuery スキーマ・View・テストを整合させる。
- 既存ファイルは再取り込みまたは移行が必要。同じチェックサムなら処理をスキップするため、日付追加を反映する再処理方法を用意する。本文ハッシュが同じ際の最新メタデータ選択も確認する。

## 段階的な実装

1. 直近の Drive 一覧取得 404 を解消し、実文書を確認する。
2. 対象日付・対象期間と出典を抽出・保存し、Silver に公開する。
3. Go の質問回答 CLI を追加する。日本時間で「先月」の期間を決め、パラメータ付き SQL で対象文書を取得する。週次文書の期間重複を含めるかは仕様として決める。
4. 取得した本文を Vertex AI の Gemini に渡し、課題と根拠を出典付きで回答する。資料がない場合は根拠がないと返す。
5. 月全体のまとめでは対象文書を網羅する。量が多い場合は文書ごとに要約して統合し、取得漏れや入力上限による省略を明示する。
6. 「過去に似た悩みは？」などの意味検索に、Vertex AI Embeddings と BigQuery Vector Search を追加する。Embedding は最新本文の content_version に対応させ、古い版や未処理チャンクを区別する。

最初の期間指定回答は日付による SQL 検索＋Gemini で実現でき、Embedding は必須ではない。これは段階的な実装案であり、既存 Phase 2 の #36 → #37 → #38 → #39 を完了したことにはならない。

```text
Drive → Go（日付抽出・本文分割）→ BigQuery Silver
                                     ↓ 対象期間の本文を取得
                                  Go → Gemini → 出典付き回答

Silver → Gold → データポータル（取り込み状況の確認）
```

Vertex AI が自動で BigQuery を読む構成ではなく、Go が取得した本文をモデルへ渡す。検証では対象期間の正確さ、欠損日付、更新後の最新版、資料不足、複数文書の網羅性、出典と回答の対応を確認する。

## dbt の位置づけ

dbt は BigQuery 内の View・集計変換に導入可能。Go による取得・分割・ロードは維持し、変換の依存関係・データ検証・説明資料を dbt で管理できる。現状は変換数が少ないため必須ではなく、まず実デモを完成させる。導入時は Terraform のデータセット・権限管理と dbt の変換オブジェクト管理を分ける。
