# 振り返り対象期間の記載形式調査

## 調査範囲と結果

2026-10-16、既存の `DRIVE_FOLDER_ID` が指定するフォルダを読み取り、そこにある Markdown 3文書のファイル名・見出し・本文の日付表記と、Drive の `description`・`properties`・`appProperties` を調べた。文書やクラウドの設定は変更していない。実文書本文・実際の日付・ファイル名・ID・URL・認証情報は、この記録に含めない。

| 確認箇所 | 結果 |
|---|---|
| ファイル名 | 全3文書に `YYYYMM-N` 形式の年月・番号がある |
| 最初の見出し | 全3文書が `# YYYYMM-N` 形式 |
| その他の見出し | 調査した日付形式の一致なし |
| 本文 | 2文書に年を含まない `M/D` 形式の候補が計3か所ある |
| 年月日 | 区切り付きの西暦年月日、日本語の西暦年月日、8桁の年月日は一致なし |
| YAML front matter | 全3文書でなし |
| Drive の追加メタデータ | `description`・`properties`・`appProperties` の返却なし |

日付形式の候補を検出した結果であり、本文中の各日付が文書全体の対象期間を意味することは確認できていない。年のない日付、複数文書への参照、本文中の出来事の日付を、開始日・終了日として採用する根拠は得られていない。日次・週次の別や、独立した複数期間の保存単位も未確定である。調査した形式以外の表記や、対象フォルダ外の文書を網羅した結果ではない。

## 実装前に決めること

1. `YYYYMM-N` の番号が何を意味するか確認する。週を表すなら、週の開始曜日・第1週の数え方・月またぎの帰属を明文化する。通し番号なら日付への変換には使わない。
2. 正確な期間の根拠をどこへ記載するか決める。例えば、今後の文書に開始日・終了日の明示欄を設ける方法がある。これは提案であり、既存文書の形式ではない。
3. 推測によるフォールバックを導入する場合は、正確な期間と区別する方法を決め、#133 の「年月ラベルから推測しない」という現在の要件を更新する。推定値を、そのまま正確な期間の列へ保存する仕様は採用しない。

現段階では取得元の優先順位や複数期間の仕様を確定していない。既存のタイトル年月による月検索は利用できる。正確な対象期間を裏付ける情報がない文書は、現行方針どおり開始日・終了日を NULL とする。

## 検証の区分

今回行ったのは実 Drive 文書の読み取り調査である。期間抽出の実装、テスト、BigQuery の期間検索検証、既存文書の再処理、本番適用は行っていない。

## Notion の作成元の追加調査

同日、ユーザーが指定した Notion テーブルと既定テンプレート、テンプレート内の3つのテーブルのスキーマを読み取った。Notion の内容・設定は変更していない。

親テーブルのプロパティは `Name`（タイトル）・`Feedback`（テキスト）・`done`（チェックボックス）だった。取得したスキーマには、対象期間の日付列や採番用の数式プロパティはなかった。既定テンプレートの名前は `YYYYMM-n` 形式だったが、取得できた内容には週番号の定義や対象期間の算出ルールは記載されていなかった。データベースの自動化設定は今回の取得結果に含まれていないため、自動採番の有無は断定しない。

テンプレート内の別テーブルには `Date`・`開始日`・`完了予定日`・`startDate` などの日付プロパティがある。ただし、それらが親の振り返り文書全体の対象期間を意味する根拠は確認できていない。これらの日付の最小値・最大値を親文書の対象期間として採用する仕様にはしない。

ユーザーによると、タイトルの番号は新規作成時の月・週・前回の番号を参照して決めている。週の区切り方、月またぎの扱い、作成した週と振り返り対象の週の関係は引き続き確認が必要である。

## 調査後に合意した規約

ユーザーは、今後のsprintを月曜日から日曜日までの7日間とし、開始する月曜日の年月・月内の順番でタイトルを決める方針を選んだ。過去分には回数と週番号が混在するため、一律には適用しない。適用開始月は、その後のユーザーの指定により2026年11月に確定した。実装・設定・検索・再処理の仕様は [sprintの対象期間](reflection-sprint-periods.md) を参照する。上記の調査時点の未確定事項と、合意後の規約を区別する。
